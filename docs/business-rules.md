# 도메인 규칙

지원사업 조사에서 "맞다/틀리다"를 가르는 규칙. 코드(파서·상태 스크립트)와 지시(SKILL.md·에이전트)가 모두 이 규칙을 구현한다.

## 용어

- **공고(announcement)**: 한 소스의 한 게시물. 키는 `(source, id)`. K-Startup은 `pbancSn`, 기업마당은 `pblancId`(`PBLN_…`), NIPA는 경로의 숫자, KOCCA는 `intcNo`, SMTECH는 `ancmId`
- **사업(program)**: 같은 지원사업이 여러 소스에 게재된 것의 묶음. 코드는 사업을 모른다 — 제목 유사도로 합치는 일은 모델이 보고서 단계에서 한다
- **프로필 축**: 창업 단계 / 지역 연고 / 대표자 특성(연령·성별·소속) / 필요한 것 / 아이템 요약. 판정은 이 다섯 축과 공고 요건의 대조다
- **실행(run)**: 한 번의 조사. `full`(전수) 또는 `diff`(직전 완료 실행 대비 증분)
- **불명**: 공고 원문에 해당 정보가 없음. "확인 못 함"과 같고 "아니오"와 다르다

## 수집 규칙

- 소스의 "모집중" 목록을 첫 페이지부터 **새 항목이 0건인 페이지가 나올 때까지** 읽는다. 페이지 수 상한(`--max-pages`)에 걸리면 그 소스는 부분 수집이고, 보고서 한계 고지에 적는다
- 같은 `id`가 두 번 나오면 뒤의 것이 앞의 것을 덮는다 (캐러셀·상단 고정 중복 제거)
- 마감일 필터(`--drop-expired`)는 **오늘보다 이전 날짜로 파싱되는 항목만** 버린다. 빈 값·"상시"·"예산 소진 시"·파싱 실패는 남긴다. 반대로 하면(못 읽는 건 버리기) 상시 모집 사업이 통째로 사라진다
- 차단된 소스는 수집 결과에서 빠지되 **빠졌다는 사실이 보고서에 남아야** 한다. 조용한 누락은 허용되지 않는다

## 검토·검증 규칙

- 후보 선별은 목록 **전체**를 읽고 한다. 키워드 필터로 대체하지 않는다 — C그룹(변형)은 키워드로 잡히지 않는다
- 후보 전건의 상세 원문을 확인한다. 예외는 diff 모드의 UNCHANGED 항목(직전 판정 승계)뿐이다
- 각 항목의 값은 원문 문장으로 뒷받침되어야 한다. 근거 없는 값은 불명이다
- 소재 요건(사업장 위치)과 접수 자격(누가 낼 수 있나)은 별개 필드다. 하나만 확인하고 다른 하나를 추론하지 않는다
- 필수 제출서류에 사업자등록증·4대보험 명부·재무제표·매출 증빙이 있으면 예비창업자 불가로 본다 — 단, 공고에 "예비창업자 포함" 문구가 **함께** 있으면 문구가 우선하고 서류는 "선정 후 제출" 가능성으로 표시한다

## 판정 규칙 (A / B / C / 제외)

| 등급 | 조건 (모두 충족) | 반드시 적을 것 |
|---|---|---|
| A | 프로필 다섯 축 그대로 신청대상에 포함 · 제외 요건 미해당 · 마감 미경과 | 자격 근거, 마감(시각), URL |
| B | 현재 미달이지만 트리거(법인 설립·투자유치·지역 이전·매출 실적)가 공고에 **명시** | 트리거 문장, 연쇄 경로(있으면) |
| C | 신청대상은 맞지만 사업 취지가 아이템과 다름 · 재서술 각도가 **구체 문장**으로 나옴 | 재서술 문장, 리스크 |
| 제외 | 위 셋 아님 | 유명 사업이면 "검토했으나 제외"에 한 줄 이유 + URL |

- 불명 항목이 있는 A는 A로 두고 "유선확인 필요"를 붙인다. 불명 때문에 B로 내리지 않는다 — 기회를 숨기는 오류가 없는 기회를 보이는 오류보다 비싸다
- 마감 3일 이내는 임박. 마감 시각이 원문에 있으면 날짜만 쓰지 않는다
- 등급 결정에 트레이드오프가 있었으면(애매한 지역 요건, 사용자 오버라이드) 결정 기록을 남긴다. 원문이 명시적이면 남기지 않는다

## diff 규칙

두 실행의 항목을 `(source, id)`로 대조한다. 비교는 **두 실행 모두에 있는 소스**에서만 한다.

| 분류 | 조건 | 처리 |
|---|---|---|
| NEW | 이번에만 있음 (공통 소스) | 전수 검토 + 상세 검증 |
| CLOSED | 직전에만 있음 (공통 소스) | 직전 A그룹·큐 `apply`였으면 "기회 소멸" 보고 + 큐 종료 |
| DEADLINE CHANGED | 양쪽에 있고 `apply_end` 다름 | 판정 유지, 마감 갱신. 직전 A그룹이면 상세 재확인 |
| UNCHANGED | 양쪽에 있고 마감 같음 | 판정 승계, 재검증 없음 |
| 새 소스 | 이번에만 크롤된 소스의 전체 | 기준 없음 → 전수 검토 |
| 미갱신 소스 | 직전에만 크롤된 소스 | diff 대상에서 제외, 보고서에 "미갱신" 명시 |

## 워크스페이스 상태 규칙

- 진행 중(`stage != done`) 실행이 있으면 새 실행을 만들 수 없다 (`--force` 제외). 끊긴 조사는 재개하거나 명시적으로 버린다
- diff 베이스라인은 `done`인 실행 중 가장 최근이다. 진행 중 실행은 베이스라인이 될 수 없다
- 큐 항목 종류: `verify`(2단계 후보 → 3단계 대기), `manual`(차단·JS 로딩·첨부 본문 → 사람이 확인), `apply`(사용자가 신청하기로 한 A), `followup`(유선확인 등), `resurvey`(다음 조사 예정일). `verify`만 `run finish`가 자동 종료한다 — 나머지는 사람이 닫는다
- 같은 종류 + 같은 `ref`(또는 `url`)가 열려 있으면 다시 추가되지 않는다
- 워크로그는 추가만 한다. 잘못된 항목은 다음 항목의 메모로 정정한다
- 프로필 축 밖의 개인정보(주민번호·계좌·연락처·상세 주소)는 어느 파일에도 쓰지 않는다
